# 设计语言：Living Org Canvas v2

**状态**：已确认，待全量重做实现（2026-08-18）  
**产品**：Ensemble  
**一句话**：以组织画布为主体的 Agent 协作工作台；界面简约、安静、高密度，复杂信息按选择逐层展开。

> 本文是新前端的设计真源。现有 `apps/canvas` 仅保留为功能参考，不构成视觉、布局或交互兼容约束。

---

## 1. 设计判断

Ensemble 的核心不是展示系统配置，而是让用户持续回答四个问题：

1. 当前正在处理什么任务？
2. 哪些 Agent 在参与，各自负责什么？
3. 工作如何流转，当前卡在哪里？
4. 用户现在是否需要介入？

因此，新界面必须坚持：

- **任务上下文优先于系统配置**
- **组织关系优先于容器和面板**
- **需要介入的事项优先于普通活动**
- **画布优先于固定三栏**
- **信息逐层展开，而不是首屏全部摊开**
- **状态变化保持位置稳定，避免界面跳动**

### 1.1 视觉基调

- 浅色优先，支持深色、跟随系统和自定义主题
- 默认使用冷白画布、炭黑文字与朱红主信号
- 大面积颜色只用于结构，不用于装饰
- 不使用霓虹、玻璃、泛光和装饰性渐变
- 不把每个对象绘制成卡片
- 不通过颜色数量表达系统复杂度

### 1.2 明确废弃

- 深蓝单色 HUD
- 顶栏堆叠 Source、Fixture、LOD、Mode 等开发控件
- 永久占宽但经常为空的 Todo 侧栏
- Group 容器内再嵌套 Seat 卡片
- 每个状态使用一种高饱和颜色
- 隐藏式双击作为唯一入口
- 持续发光或满屏循环动画
- 中英文、技术 ID 和产品文案混杂显示
- 用产品名称的词源设计界面隐喻

## 2. 产品外壳

新布局不是固定左中右三栏，而是：

> **窄导航轨道 + 全尺寸画布 + 按需检查器**

```text
┌──────┬────────────────────────────────────────────┐
│      │ Workspace / Run / Stage / Primary action  │
│ 全局 ├───────────────────────────────────┬────────┤
│ 导航 │                                   │        │
│ 轨道 │          Living Org Canvas        │ 检查器 │
│      │                                   │ 按需出 │
└──────┴───────────────────────────────────┴────────┘
```

### 2.1 全局导航轨道

默认宽度 `52–64px`，只承载跨工作区的稳定入口：

- Workspace
- Runs
- Attention 数量
- Settings

规则：

- 不在此处重复展示组织树
- 标签通过 Tooltip 或展开面板补充
- 展开后形成临时导航面板，不长期压缩画布
- 当前 Workspace 必须始终可辨认
- 没有待处理事项时只显示入口，不显示空列表

### 2.2 上下文栏

高度目标 `48–56px`，只回答：

- 当前 Workspace
- 当前 Run 或待启动任务
- 当前阶段和整体状态
- 一个主操作
- 必要的次级操作菜单

正式产品界面禁止出现 Mock fixture、内部 LOD、事件源和调试模式切换。调试能力进入独立开发面板。

### 2.3 画布

- 默认占据除导航和上下文栏之外的全部空间
- 无永久点阵、星空或装饰背景
- 对齐辅助线只在拖动或布局调整时出现
- 画布缩放、位置和展开状态按 Workspace 记忆
- 画布空白区域用于平移和取消选择，不承担业务操作

### 2.4 检查器

- 未选择对象时不出现
- 宽屏停靠，普通窗口覆盖，不长期挤压画布
- Seat、Group、Packet、Attention 使用同一检查器容器
- 内容按对象变化，容器结构保持稳定
- 打开检查器时，只有目标被遮挡才调整视口

## 3. Workspace 与 Runner

Runner 是 Workspace 创建时选择的业务配置，不是顶栏临时模式。

### 3.1 创建 Workspace

最小流程包含：

1. Workspace 名称
2. 项目目录或仓库路径
3. 默认 Runner
4. Runner 所需的权限和参数确认
5. 创建后进入空画布或选择编排模板

规则：

- Runner 列表只显示当前平台可用且通过检测的选项
- 无可用 Runner 时明确说明缺少什么，不创建不可运行的 Workspace
- 修改 Workspace 默认 Runner 只影响后续 Run
- 运行中的 Run 固定其启动时的 Runner 配置
- Runner 技术参数进入 Workspace Settings，不占用主画布

### 3.2 Workspace 切换

- 切换后恢复对应画布位置、选择状态和最近 Run
- 跨 Workspace Attention 点击后直接定位到对应对象
- 切换期间先更新 Workspace 身份，再加载画布内容
- 不允许旧 Workspace 的选中态短暂出现在新 Workspace 中

## 4. 画布对象

### 4.1 Seat

Seat 是身份和状态锚点，不是信息卡片。

标准 Seat 由以下部分组成：

- `40–48px` 身份标记
- 名称
- 职责或 Role
- 一行当前动作
- 状态指示
- Attention 标记
- 展开或进入子组织的明确控件

规则：

- 默认宽度稳定，动态内容不得改变节点布局
- 长名称截断，但检查器中显示完整值
- Runner 名称不在默认节点上展示
- 技术 ID 不在默认节点上展示
- 选择状态使用轮廓、定位标记或主信号，不增加大面积背景
- Hover 只补充即时信息，不复制完整检查器

### 4.2 Group

Group 使用空间关系表达归属：

- 区域标题
- 低对比边界或局部底色
- 展开、折叠和聚焦控件
- 子树状态汇总

禁止使用大圆角虚线卡片包裹一组 Seat。Group 边界不能比 Seat 和活跃路径更醒目。

### 4.3 Edge

- 默认低对比、细线、方向可辨
- 只表示真实的组织或 Handoff 关系
- Hover Seat 时高亮直接相关 Edge
- 非相关路径降低对比，但不完全消失
- Edge 不承载大段文字

### 4.4 Packet 与 Handoff

Handoff 使用短暂、明确、有方向的脉冲：

1. 起点短促响应
2. 脉冲沿 Edge 向目标移动
3. 目标 Seat 短促响应
4. 动效结束后保留最近交付状态，不持续闪烁

规则：

- 同时有多个 Handoff 时限制高强调脉冲数量
- 标签只显示 artifact 名称、类型或简短动作
- 用户可点击最近 Packet 查看交付详情
- 减少动态模式使用路径颜色变化和目标高亮代替位移

## 5. 状态语言

协议可以保留细粒度状态，界面默认收敛成五类视觉语义：

| 视觉语义 | 内部状态 | 默认表达 |
|---------|----------|---------|
| 就绪 | `idle` | 中性轮廓 |
| 执行中 | `planning`, `working`, `tooling` | 活跃状态 + 具体动作 |
| 等待 | `waiting_human`, `waiting_peer` | 等待标记 + 等待对象 |
| 异常 | `blocked`, `error` | 危险标记 + 原因入口 |
| 完成 | `done` | 完成标记，降低持续强调 |

颜色只能辅助语义，图标、文案和结构必须能独立表达状态。

### 5.1 优先级

```text
需要用户处理 > 异常 > 执行中 > 普通等待 > 完成 > 就绪
```

折叠 Group 或父 Seat 必须汇总子树中的 Attention 和异常，不让关键状态因折叠消失。

## 6. 交互模型

### 6.1 Seat

| 动作 | 行为 |
|------|------|
| Hover 300ms | 显示目标、当前动作、耗时和最近输出；高亮关联路径 |
| 单击 | 选择 Seat 并打开检查器 |
| 展开控件 | 原地展开或折叠子树 |
| 进入控件 | 聚焦进入子组织并显示返回路径 |
| `Enter` | 对当前键盘焦点执行选择 |
| `Esc` | 关闭当前浮层、检查器或选择状态 |

双击可以作为效率手势，但不得是唯一入口。

### 6.2 画布

- 滚轮或触控板缩放以指针位置为中心
- 拖动空白区域平移
- `Fit` 优先适配 active path，其次适配当前展开范围
- 聚焦对象后保持可见上下文，不把其它对象全部隐藏
- 布局变化使用稳定过渡，不让对象在状态更新时重新排布

### 6.3 层级退出顺序

`Esc` 按以下顺序工作：

1. 菜单或弹层
2. 模态对话框
3. 检查器
4. 当前选择
5. 聚焦子组织

---

## 7. Attention 与人工介入

Attention 包括审批、提问、异常和扩编确认。

### 7.1 节点表达

- Seat 旁显示简短标记和一行摘要
- 不在画布上长期展开完整审批卡
- 多个事项聚合为数量，最高优先级决定视觉状态
- 点击后在检查器中展示上下文、相关产物和操作

### 7.2 操作

- 简单的通过、打回可以在上下文完整时就地完成
- 需要评论、对比产物或调整参数时进入检查器
- 提交后在原位置显示进行中、成功或失败
- 禁止只通过全局 Toast 告知操作结果

### 7.3 全局入口

- 导航轨道显示跨 Workspace 待处理数量
- 面板按优先级和 Workspace 分组
- 空状态不占主界面空间
- 点击事项后完成 Workspace 切换、对象定位和检查器打开

---

## 8. 检查器结构

检查器不是卡片集合，而是带分隔线的连续工作区。

Seat 检查器建议顺序：

1. 身份、状态和当前动作
2. 需要用户处理的事项
3. 当前输入与输出
4. History
5. Prompt 与人工指令
6. Tools 与 Runner 信息
7. 子组织

规则：

- 默认显示当前最重要内容，不默认展开所有历史
- Tab 只用于互斥视图，不用于把任意内容切碎
- 重要操作靠近对应内容
- 危险操作进入明确菜单并要求确认
- 技术日志进入 Inspect 或 Diagnostics，不污染默认视图

## 9. 主题与视觉系统

完整规则见 [ssot/design-system.md](ssot/design-system.md)。本文件只锁定体验约束。

### 9.1 默认主题

- 浅色优先
- 冷白或浅灰画布
- 炭黑主文字和导航骨架
- 朱红作为主操作、选择和用户介入信号
- 蓝色用于系统执行
- 琥珀用于等待
- 红色用于异常
- 绿色用于完成

默认颜色不是组件常量。所有组件必须通过语义 Token 使用颜色。

### 9.2 形状

- 基础圆角：`4px`, `6px`, `8px`
- 头像和状态点可使用圆形
- 不把标签和普通状态默认做成胶囊
- 阴影只用于浮层与层级分离
- 页面区块不使用浮动卡片样式

### 9.3 字体

- UI 字体必须覆盖中英文并具有稳定字宽和清晰数字
- 技术 ID、路径和日志使用独立等宽字体
- 品牌名不使用装饰字体主导工作界面
- 字号不随视口连续缩放

## 10. 动效

| 类型 | 建议时长 | 用途 |
|------|----------|------|
| 即时反馈 | `80–120ms` | 按压、选择、Focus |
| 结构过渡 | `160–220ms` | 检查器、菜单、节点状态 |
| 画布变化 | `220–320ms` | 展开、折叠、聚焦 |
| Handoff | `350–700ms` | 有方向的路径脉冲 |

规则：

- 动效必须表达因果、方向或层级
- 不使用持续呼吸、无限泛光和装饰循环
- 状态更新不得触发全画布入场动画
- 遵守 `prefers-reduced-motion`
- 大规模画布下优先保证平移和缩放响应

## 11. 文案与多语言

完整规则见 [ssot/i18n.md](ssot/i18n.md)。

- 一个界面会话只使用一种 UI 语言
- 产品文案不混入内部枚举、运行 ID 和开发术语
- 状态使用用户可理解的动词或结果
- 不在按钮中写解释性长句
- 不使用依赖英文长度的固定宽度
- 用户内容、Agent 输出和 UI 文案必须区分来源
- UI 语言与 Agent 输出语言分别配置

## 12. 平台与窗口适配

完整规则见 [ssot/platform-adaptation.md](ssot/platform-adaptation.md)。

### 12.1 桌面断点

| 窗口宽度 | 行为 |
|----------|------|
| `>=1440px` | 检查器可停靠 |
| `1024–1439px` | 检查器覆盖画布 |
| `<1024px` | 进入受限紧凑模式，不作为首发主工作尺寸 |

建议最小窗口为 `1024x680`。

### 12.2 平台一致与差异

必须一致：

- 信息架构
- 状态语义
- 画布操作
- Runner 和 Run 的业务行为

允许适配：

- 标题栏和系统菜单
- `Ctrl` / `Cmd` 快捷键
- 字体渲染和滚动条
- 窗口装饰、DPI 和安全区域

## 13. 可访问性

- 正文和控件文字达到 WCAG AA 对比度
- 所有业务状态不能只靠颜色表达
- 所有主要操作可以键盘完成
- Focus 环不能被主题关闭
- 图标按钮提供可访问名称和 Tooltip
- 画布对象提供可导航的替代结构
- 高对比模式下关闭非必要底色和阴影
- 文本放大后不遮挡业务操作

## 14. 验收场景

### A. 创建 Workspace

- 用户选择目录和 Runner
- 系统明确显示 Runner 是否可用
- 创建后进入干净的画布
- 正式界面没有开发态选择器

### B. 单 Agent

- 一个 Seat 在画布中自然成立，不显空洞
- 可启动 Run、查看状态、处理 Attention 和查看产物
- 检查器关闭时画布保持完整

### C. 多 Agent

- 用户在五秒内辨认参与者、活跃路径和等待用户的位置
- Handoff 脉冲方向清晰，结束后不持续闪烁
- 非相关路径保持可见但降低强调

### D. 深层组织

- 展开、折叠和进入子组织都有可见控件
- 折叠后关键 Attention 和异常仍可见
- 结构变化不导致全画布无意义重排

### E. 主题与语言

- 浅色、深色和跟随系统均保持语义一致
- `zh-CN`、`en-US` 不出现布局溢出和混合语言
- 减少动态和高对比设置有效

### F. 平台

- Windows、macOS、Linux 安装后无需用户安装额外开发环境
- Backend 能随应用可靠启动和退出
- 数据写入平台应用数据目录

## 15. 实现边界

允许：

- 删除并重写现有 `apps/canvas`
- 重做组件、状态结构和 API 客户端
- 重新定义 Runtime API 和持久化模型
- 删除只服务旧演示界面的 Fixture 和交互

要求：

- 新模型必须先进入产品、协议和平台文档
- 不为旧演示数据添加兼容层
- 业务状态、保存语义和 Runner 生命周期必须端到端定义
- 主题、语言和平台差异不得散落在业务组件条件分支中
- 新实现以 [specs/m6-product-rebuild.md](specs/m6-product-rebuild.md) 为验收入口
